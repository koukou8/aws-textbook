# 特設ページ(解説ページ)ジェネレーター

問題集でつまずいた問題やキーワードをもとに、周辺知識まで含めた解説ページを
`data/topics/` に追加する。ページは `topic.html?id=<id>` で表示され、
ダッシュボード(index.html)の「特設ページ」セクションに自動で一覧表示される。
**topic.html / js/topic.js / js/dashboard.js を編集する必要はない** — データファイルの追加だけで完結する。

## ワークフロー

### 1. トピックを決める

渡された問題文・解説・キーワードから「このページが答えるべき問い」を1つに絞る。
良い特設ページは「問題の正解の暗記」ではなく **判断基準の理解**(どんな要件のときに何を選ぶか)を提供する。

- 問題が渡された場合: その問題の「決め手」と、対比されていた選択肢群(例: ゲートウェイ型 vs インターフェイス型)をトピックにする。
- キーワードだけの場合: そのキーワードと、試験・実務で必ず対比される周辺概念をセットで扱う。
- 複数の独立した論点が混ざっている場合: 1ページ1トピックが原則。主要な1つでページを作り、残りは「次に作れるページ」として最後に提案する(ユーザーが複数明示した場合はページを複数作ってよい)。

### 2. 事実を確認する

**存在しないサービス名・機能名・制限値・料金を書かない。** これが品質の生命線。
少しでも自信がない仕様は WebSearch / WebFetch でAWS公式ドキュメント(または該当技術の公式ドキュメント)を確認する。
確認できなかった数値・仕様は書かずに省く。`references` に載せるURLはでっち上げず、
確実に存在するトップレベルのユーザーガイドや FAQ ページを使う(docs/content-guide.md の reference ルールと同じ)。

また、同じ論点を扱う既存教材が `data/` 配下(basics / saa / cloudops / aif)にないか
`grep -ril "<キーワード>" data/` で確認し、あれば**用語・訳語・枠組みを既存教材と揃える**
(例: AIF教材では「検索拡張生成(RAG)」「状況に応じた学習」という表記を使っている)。
教材と特設ページで訳語がぶれると読者が別概念だと誤解する。

### 3. データファイルを書く

まず見本を読む(スキーマと文体の実例): `data/topics/vpc-endpoint-types.js`(AWSサービス対比型)と
`data/topics/rag-vs-fine-tuning.js`(概念対比型)。
`data/topics/<id>.js` を作成する。id は小文字英数字とハイフンのみ(例: `s3-storage-classes`)。
既存の `data/topics/index.js` にある id と重複させない。

```js
// 特設ページ: <タイトル>
export const topic = {
  id: "<id>",                     // ファイル名と一致させる
  title: "...",                    // 論点が一目でわかるタイトル(「AとB」より「AとBの使い分け」)
  description: "...",              // ダッシュボードカード用の1〜2文(20字以上)
  exam: "SAA-C03",                // 関連試験コード。この教材の対象は SAA-C03 / SOA-C03 / AIF-C01。
                                   // 複数該当は "SAA-C03 / SOA-C03"、他資格はその試験コード、資格と無関係なら null
  services: ["Amazon S3"],         // 主要サービス・キーワード(1〜4個。カードにバッジ表示される)。
                                   // サービス名以外の概念キーワード(例: "RAG")も可
  createdAt: "YYYY-MM-DD",        // 今日の日付
  source: {                        // きっかけの問題。キーワードだけから作る場合は null
    question: "...",               // 問題の要約(20字以上)
    point: "...",                  // その問題の決め手・つまずきポイント(15字以上)
  },
  sections: [
    { heading: "...", html: `...` }, // 3〜5セクション。html はテンプレートリテラルで
  ],
  references: [
    { label: "...", url: "https://..." }, // 公式ドキュメントのみ。1〜4個
  ],
};
```

**著作権上の注意**: 問題集の問題文は著作物。`source.question` にコピペ原文をそのまま保存せず、
必ず自分の言葉で要約する(「〜という趣旨の問題」の形が書きやすい)。選択肢の丸写しもしない。

**セクション構成の型**(そのまま使うと書きやすい):

1. **結論・試験での決め手** — 読者が最初に欲しいのは判断基準。1行に集約できるならcalloutで強調する
2. **仕組み・全体像** — なぜそうなるのかを理解させる(暗記を理解に変える)
3. **対比・比較表** — 混同しやすい選択肢との違いを表で整理(`table-wrap` 必須)
4. **典型パターン・試験での注意** — 「この要件ならこれ」のパターン列挙と、ひっかけへの警告

**図解を1つは入れる。** 既存の特設ページはすべて図を持っている。文章と表だけで説明しきれる論点でも、
「境界線がどこにあるか」「パケット/リクエストがどの順で何を通るか」「対策ありとなしで何が変わるか」は
図にすると一段わかりやすくなる。置き場所は「結論」か「仕組み」のセクションが基本。
書き方(`<figure class="diagram">` + インラインSVG + `d-*` クラス)は docs/content-guide.md の
「sections[].html で使える要素」に仕様と雛形がある。既存ページのSVGをコピーして作り替えるのが早い:

- 対比型(2パネルを破線で区切る): `data/topics/confused-deputy-external-id.js`、`data/topics/vpc-endpoint-types.js`
- フロー型(横一列 + 注釈 + 戻り矢印): `data/topics/transit-gateway-routing.js`
- 境界型(どこまでが対象範囲かを示す): `data/topics/flow-logs-troubleshooting.js`
- 表形式の対比(行=サービス、列=分類): `data/topics/cloudtrail-event-types.js`

**本文の規約**は docs/content-guide.md の「2. 教材(章)スキーマ」の
「sections[].html で使える要素」と「JavaScript構文上の注意」、「3. 文体・表記」に従う。要点:

- 使える要素は `<p>` `<strong>` `<em>` `<code>` `<ul>/<ol>` `<h4>` `<pre><code>` 表(`table-wrap`で包む) callout 3種 図解(`figure.diagram` + インラインSVG) 公式ドキュメントへの`<a>`のみ。`<script>` `<style>` `<img>` と Tailwind クラスの直書きは禁止(スタイルは自動適用される)
- html はバッククォートのテンプレートリテラルなので本文にバッククォートを書かない。`${` は `\${` にエスケープ
- 日本語「です・ます」調。サービス名は公式表記(AWS Lambda / Amazon SQS の接頭辞を間違えない。2025年以降の名称を使う)

### 4. レジストリに登録する

`data/topics/index.js` の `topicIds` 配列の **先頭** に id を追加する(新しいページほど上に表示される)。

### 5. 検証する

```bash
node scripts/validate.js data/topics/<id>.js
```

エラー0件になるまで修正する。レジストリとの整合(id一致・重複)は全体検証
`node scripts/validate.js` でも確認できる。CSSのリビルドは不要(使える要素だけで書いていれば既存CSSで表示される)。

### 6. 報告する

最終応答で以下を伝える(本文は貼らない):

- 追加したページのタイトルと URL(`topic.html?id=<id>`。ローカルは `npm run serve` で http://localhost:4173/topic.html?id=<id>)
- カバーした論点とセクション構成(1行ずつ)
- 事実確認のために参照した公式ドキュメント
- 提案: 関連して作れそうな次のトピックがあれば1〜2個

コミットは頼まれた場合のみ(commit-push スキルを使う)。

## 品質基準

- **問題の再解説で終わらせない。** 元の問題集の解説を読んでもわからなかった人が読者。「なぜその答えになるのか」の仕組みと、「次に似た問題が出たらどう判断するか」の基準まで書く。
- 対比ペア(Multi-AZ vs リードレプリカ、SQS vs SNS など)は積極的に表で整理する。試験は「似たものの使い分け」を問う。
- 1ページの分量目安はセクション3〜5個、各300〜700字。長くなりすぎるなら論点を分割して別ページにする。
- ひっかけ選択肢(NATゲートウェイでも到達はできる、など)には「なぜ不正解になるか」を明記する。誤答の理由がわかると理解が定着する。
